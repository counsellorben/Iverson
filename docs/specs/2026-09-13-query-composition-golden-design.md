# A query-side golden in the ingest contract — design

**Date:** 2026-09-13
**Parent:** the query-prefix extension merged in `536a5b0` (`queryPrefixes` / `defaultQueryPrefix` +
`ingest.query_prefix_for`), and the whole-branch review of that work, which recorded that
`query_prefix_for` has no standing cross-language check while `document_prefix_for` has one.
**Status:** design, approved.

---

## 1. The question

`ingest-contract.json` now carries query prefixes, and `ingest.py` resolves them. Nothing checks that
Python's resolution agrees with the server's. The document side has had that check since the contract
existed: `verify_contract` composes the golden's own `text` through Python's `document_prefix_for` and
compares against the `composed` string C# emitted.

> **Should `query_prefix_for` get the same standing replay, and should the strict form check both
> compositions in one pass?**

Yes to both. The design is the smallest change that achieves it.

### Why it is worth more than closing a symmetry gap

| family | document prefix | query prefix |
|---|---|---|
| `nomic-embed-text` | `search_document: ` | `search_query: ` |
| `snowflake-arctic-embed` | **empty** | `Represent this sentence for searching relevant passages: ` |
| `BAAI/bge-base-en-v1.5` | **empty** | `Represent this sentence for searching relevant passages: ` |
| `BAAI/bge-small-en-v1.5` | **empty** | `Represent this sentence for searching relevant passages: ` |

**Three of the four document goldens are identity checks** — `"" + text == text`. That does not make them
worthless: a lookup returning the *query* prefix by mistake is caught on all four families today. What an
identity golden cannot catch is a prefix that wrongly **collapses to empty** — caught on nomic, missed on
arctic, bge-base and bge-small. **None of the four query goldens is an identity**, so the query golden closes
the collapse-to-empty blind spot on exactly those three families — including bge-base, the model this
project actually runs.

## 2. Design

### 2.1 The C# emit

`IngestContractTests.EmitContract` gains `golden.queryComposition`, mirroring `documentComposition`
(`IngestContractTests.cs:124-135`) exactly: a `Dictionary<string, object>(StringComparer.Ordinal)` with one
entry per family in `EmbeddingPrefixes.Table` plus `__default__`, each `{ text, composed }` where `text` is
the existing `SampleText` const and `composed` is `ComposeQueryInput(prefix.Query, SampleText)` — with
`EmbeddingPrefixes.DefaultQuery` for the `__default__` entry.

The composer is reached the way the document side reaches its own:
`NonPublicStatic(typeof(EmbeddingService), "ComposeQueryInput")`. That helper throws with the member it
could not find, so a rename fails the emit loudly rather than silently emitting a stale value.

`StringComparer.Ordinal` is not a style choice here and is used for the same reason the document side uses
it: Python resolves the same family through a case-sensitive `dict.get()`.

### 2.2 The regenerated contract

`ingest-contract.json` is regenerated by the emitter, never hand-edited:

```
IVERSON_REGENERATE_INGEST_CONTRACT=1 dotnet test Iverson.Server/Iverson.Api.Tests/Iverson.Api.Tests.csproj --filter IngestContract
```

The same command **without** the environment variable is the drift gate, and proving it green against the
committed copy is the verification that the emit and the file agree.

### 2.3 The Python replay

`verify_contract` (`ingest.py:427`) today resolves one prefix, reads one golden, and compares once. It
becomes a comparison over **both sides in one pass** — for each of (document, `document_prefix_for`,
`documentComposition`) and (query, `query_prefix_for`, `queryComposition`): resolve the prefix, take the
family's case (falling back to `__default__`), compose the case's own `text`, and compare against its
`composed`.

Composing from the golden's own `text` — rather than recovering the input by stripping the prefix back off
`composed` — is what makes this a cross-language check instead of a tautology. That property is inherited
unchanged; it is the reason the existing check is worth anything, and it applies identically to the query
side.

`require_known_family` requires the family to be present in **both** goldens. This is symmetry, not added
detection power: the two goldens carry identical key sets by construction, so a broken `family()` produces a
string already absent from `documentComposition`, and today's single-sided check already rejects it.
Requiring both is what keeps the check correct if those key sets ever stop matching.

The anti-masking argument is what makes the strict form load-bearing at all. With three empty document
prefixes, a `__default__` fallback produces the *correct* composition for those three families, so the
composition comparison alone cannot separate a broken `family()` from a working one — `require_known_family`
is the only thing that does.

### 2.4 Error handling

Unchanged in kind: `sys.exit` non-zero, before `--drop` acts, for the same reason it does today. Unchanged
in kind does not mean unchanged in text — the current messages name `golden.documentComposition` literally
(`ingest.py:456-458`), so both the missing-family message and the mismatch message must name **which side**
diverged. The distinction is the diagnostic: a document mismatch implicates the ingest write path, a query
mismatch implicates the search path and anything embedding queries Python-side.

`_verify_algorithm_goldens()` is delegated to exactly as it is now, after both comparisons rather than
after one.

### 2.5 Where it runs

No new mechanism and no new call site. `ingest.py:770` already loops the strict form over every family the
contract carries with a `:probe-tag` suffix, and `:771` calls the permissive form for the real `--model`.
Both call sites get the query side for free because the function they call covers it.

## 4. Out of scope

- **`Iverson.ClientConformance`.** `VectorSearchScenario` seeds five rows, searches at `TopK = 50` filtered
  to a run-unique marker, and asserts **set** equality via `Except` — deliberately, per its own comment at
  `:101-106` ("exact set comparisons rather than prefix comparisons"). A prefix regression changes ordering,
  not membership, so the scenario cannot fail on one. Making it able to would require an ordering assertion
  and a fixture engineered so the prefix flips order — fragile, model-dependent, and a reversal of a recorded
  design choice.
- **A Python test runner for `ingest.py`.** None exists. The replay's coverage comes from running on every
  ingest, which is how the document side has always been covered.
- **The server-side query-prefix path.** Already covered directly by
  `EmbeddingServiceTests.cs:452 EmbedQueryAsync_PrependsTheResolvedPrefix` and the per-family
  `EmbedQueryAsync` cases at `EmbeddingServiceResolverTests.cs:108,152,171`. The gap is Python-side and
  cross-language, not C#-side.
- **Any change to prefixes, families or the composition rule.** This design pins what exists; it does not
  alter it.

## 5. Known issues accepted as out of scope

- **The replay runs on ingest, and the query prefix is not consumed there.** Nothing automatically executes
  `ingest.py`, so a divergence introduced today is caught at the next ingest rather than at the next commit —
  and this is **not** the same exposure the document side has. `ingest.py`'s `main()` runs the replay at
  `:769-771` and resolves the document prefix at `:807-808`, so no document-prefix use is reachable without a
  passing replay; `query_prefix_for`'s only caller, `aspect_vectors.py:633`, never calls `verify_contract`.
  The query golden is therefore verified on every ingest and on no query embedding. Accepted deliberately:
  closing it means either gating that consumer or giving the resolver an exit side effect, both larger than
  what was asked for.
- **A `family()` that breaks in a way that still produces a real contract key** would defeat the strict
  check on both sides at once. `require_known_family` rejects a family string that is not a key; it cannot
  reject a wrong-but-valid key. No available check closes that, and the two sides sharing one `family()` is
  what makes the shared failure possible.
