## 2. Literal-wrongness findings

### 2.1 — The abort's summary line names a cause the counter cannot determine, and the spec's own worked example falsifies it

**Description.** §3 specifies the abort's single output verbatim: `"… after {Count} consecutive failures — the engagement store appears unavailable."` But the same section routes two distinct fault domains into that one counter: `Failed` outcomes (engagement store) *and* the worker's `catch` at `:74`, which receives the propagating class. §2 of the spec names that class's canonical member itself — "A Qdrant `Unavailable` is the worked example." Under a Qdrant outage the sweep reaches the threshold having just issued five **successful** StarRocks aggregate queries; the design then logs that the engagement store appears unavailable. The line is not merely imprecise — the mechanism that emitted it has, in the same five iterations, demonstrated the opposite. Since this log line is the *entire* observable product of the new mechanism, the design's asked-for output is wrong on a fault class the design explicitly admits into the counter.

The consequence is operational, not cosmetic: today a Qdrant outage or a broken collection/api-key path shows up as N loud per-parent errors naming the actual failing call. After this change it shows up as six lines every ten minutes, five of them the worker's generic "Failed to update parent" and the sixth misdirecting the reader to StarRocks.

**Evidence (file:line).**
- `docs/specs/2026-09-13-popularity-sweep-fault-abort-design.md` §2 ("A Qdrant `Unavailable` is the worked example") and §3 (`"the engagement store appears unavailable"`, and "the worker's existing `catch` at `:74` increments the same counter").
- `PopularitySignalConsumer.cs:134` — `catch (RpcException ex) when (ex.StatusCode == StatusCode.NotFound)`: every other Qdrant status propagates.
- `Iverson.Vector/IntelligenceVectorService.cs:88-99` — `SetPayloadAsync` has no catch and no retry; the Qdrant client's exception reaches the caller unchanged.
- `PopularitySignalConsumer.cs:98`, `:99`, `:127` — `ResolveCollectionName`, `KeyToUlong`, `MintScopedApiKey` sit outside any catch that could convert their failures; each is a further non-engagement-store member of the same class (R3-M cells 3 and 4).
- `PopularitySignalReconciliationWorker.cs:74` — the receiving `catch` is unfiltered `catch (Exception ex)`.

**Proposed fix.** Replace the message body so it states what the counter actually observed and points at the per-parent lines that carry the real cause, and add one sentence to §3 recording why it cannot name a store:

```csharp
logger.LogError(
    "[PopularitySignalReconciliation] Abandoning sweep for signal={Signal} after {Count} " +
    "consecutive parent-update failures — see the preceding per-parent errors for the cause. " +
    "Retrying at the next sweep in {Minutes} minutes.",
    signal.Relation.SanitizeForLog(), consecutiveFailures, SweepInterval.TotalMinutes);
```

plus, in §3, after "increments the same counter": *"The counter therefore spans two fault domains — a `Failed` outcome (engagement store) and a propagating exception (Qdrant, collection resolution, api-key minting). It cannot distinguish them, so the summary line must not name a store."*

`Evidence:` [totality] the increment set is fully enumerated in §0 row R3-M (seven cells, each dispositioned); cells 3 and 4 are non-engagement-store members, confirmed by read of `PopularitySignalConsumer.cs:98,99,127,134` and `IntelligenceVectorService.cs:88-99` (no catch/retry on the Qdrant write). [negative] the fix changes only a format string and spec prose — no control flow, no counter semantics, no operand list change: the three placeholders (`{Signal}`, `{Count}`, `{Minutes}`) and their three arguments are unchanged from the spec's own snippet, whose operand availability is verified in §0 row D4. What would have falsified this finding: a filtered `catch` at `PopularitySignalReconciliationWorker.cs:74` that admitted only engagement-store exception types, or a design that kept two counters — neither exists in the spec or the code.

### 2.2 — "It would break both tests" is false; the propagating-path contract has no test that a catch-all would fail

**Description.** §2 forbids converting the fifth path into `Failed` and grounds that instruction in a guardrail: *"it would break both tests and the contract they encode."* Neither cited test would break. Both are outcome-agnostic — they assert only that nothing escapes and that the sweep continues — and a swallowing `catch { log; return Failed; }` around the Qdrant write satisfies both. The spec therefore rests a "do not do X" instruction on a safety net that does not exist: an implementer or a later refactor that folds the residual class into `Failed` (a natural simplification, since the sweep counts it as a failure either way) gets a fully green suite while silently ending the contract the spec is trying to preserve — "it must not be silently swallowed by `UpdateAsync` itself", which is what keeps the consumer's own per-signal `LogError` (`PopularitySignalConsumer.cs:226-231`) and the worker's `LogError` (`PopularitySignalReconciliationWorker.cs:76-78`) firing with the real exception attached.

**Evidence (file:line).** Complete assertion inventory of both cited tests:
