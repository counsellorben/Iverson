# Critical Security Review — Iverson.Server (Round 2)

**Code inputs:** `Iverson.Server/Iverson.Api/`, `Iverson.Server/deploy/helm/`
**Focus hint (user-supplied):** `/admin-api catchall`
**Date:** 2026-08-25 · **Reviewed at:** `main@4770a52`
**TMA grounding:** none supplied this round — no TMA cross-link field on findings.
**Prior art:** `docs/criticalreviews/2026-07-16-iverson.server-critical-security-review-1.md` (round 1).

## What this round was asked to answer

CDR round 6 flagged that the designed `/admin-api(/|$)(.*)` Ingress is a catch-all which would
newly route port 8081's `AllowAnonymous` endpoints through the ingress. CSR round 1 on
`Iverson.AdminUI/` could not assess it — wrong scope. This round does.

**The headline result is that the premise was half wrong, in the more alarming direction.** The
anonymous endpoints are **not** confined to port 8081. They are served on the gRPC listener (8080)
as well, and 8080 is the port the *existing* api Ingress already routes `/` to. This was confirmed
by running the requests, not by reading the routing table.

**Scope note:** the `/admin-api` Ingress **does not exist in the tree** — `grep -rn "admin-api"`
across all YAML/C#/TS returns one unrelated comment. It is specified in
`docs/specs/2026-08-25-admin-console-landing-page-design.md` and not yet implemented. Findings
about it are therefore **pre-implementation** and are scored separately from the current tree (see
§3). This is the cheapest possible moment to raise them.

## Pass 1 — Attack surface

### The anonymous endpoint inventory (complete)

`grep -rn "AllowAnonymous" Iverson.Server/Iverson.Api/` returns exactly seven sites:

| Endpoint | Line | Method | Side effects when called |
|---|---|---|---|
| `/metrics` | `Program.cs:275` | GET | none (read) — 121,797 bytes, 22 metric families |
| `/health/live` | `Program.cs:299` | GET | none |
| `/health` | `Program.cs:301-334` | GET | **Postgres query + StarRocks check + Qdrant collection ensure + Kafka produce** |
| `/probe/sql` | `Program.cs:336-340` | GET | Postgres `SELECT 1` |
| `/probe/starrocks` | `Program.cs:342-346` | GET | StarRocks health check |
| `/probe/vector` | `Program.cs:348-352` | GET | **Qdrant `EnsureCollectionAsync`** (write) |
| `/probe/kafka` | `Program.cs:354-359` | **POST** | **Kafka `ProduceAsync`** (write) |

Everything else is gated: `/admin/*` by `RequireAuthorization("Operator")` (`Program.cs:373,380,392`),
`/v1/traces` by `RequireAuthorization()` (`:460`), the gRPC services by the
`RequireAuthenticatedUser()` fallback policy (`:143-145`) plus per-service policies (`:444-445`).

### The listener/port model — and why the "8081-only" premise fails

`appsettings.json:9-17` defines two Kestrel endpoints: `Grpc` on `*:8080` (`Protocols: Http2`, h2c)
and `Http` on `*:8081` (`Protocols: Http1`). **ASP.NET Core endpoint routing is listener-agnostic.**
`grep -n "RequireHost"` across `Program.cs` returns nothing, so no endpoint is bound to a specific
listener. Every route above is served on **both** ports; the only thing separating them is the wire
protocol each listener will accept.

That is the crux. "REST is on 8081" is true as a *client convenience* statement (a plain HTTP/1.1
GET to 8080 gets 400, because 8080 speaks only h2c). It is false as a *security boundary* statement.
A client that speaks h2c reaches every one of those endpoints on 8080.

**Verified live** against the running compose stack:

```
$ curl --http2-prior-knowledge http://localhost:8080/metrics
HTTP=200 proto=2 size=121797

$ curl --http2-prior-knowledge http://localhost:8080/health
HTTP=200  {"status":"healthy","checks":{"postgres":true,"starrocks":true,"qdrant":true,"kafka":true}}

$ curl --http2-prior-knowledge http://localhost:8080/probe/sql        → 200 {"connected":true,...}
$ curl --http2-prior-knowledge http://localhost:8080/probe/starrocks  → 200 {"connected":true,...}
$ curl --http2-prior-knowledge http://localhost:8080/probe/vector     → 200 {"connected":true,"collection":"iverson-probe",...}
$ curl -X POST --http2-prior-knowledge http://localhost:8080/probe/kafka
HTTP=200  {"produced":true,"topic":"iverson.probe",...}
```

All six, anonymous, on the gRPC port.

## Pass 2 — Findings

### Finding #1: The designed `/admin-api` catch-all would publish the entire anonymous REST surface to the internet

**Vulnerability:** Broken Access Control / Security Misconfiguration — A01, A05
**Severity:** High
**Confidence:** High (design is explicit and endpoint behaviour is empirically confirmed; the Ingress is not yet implemented, hence not Confirmed)
**Attack Complexity:** Low

**Location:**
- File: `docs/specs/2026-08-25-admin-console-landing-page-design.md` (Design 1, Transport) — **not yet implemented**
- Related: `Iverson.Server/Iverson.Api/Program.cs:275,301-359` (the anonymous endpoints the rule would expose)

**Risk & Exploit Path:**
The spec calls for a new Ingress with a single `pathType: ImplementationSpecific` path
`/admin-api(/|$)(.*)` and `rewrite-target: /$2`, backed by the api service on port **8081**. The
capture group is `(.*)` — unanchored and unrestricted — so the rule matches *every* path under the
prefix and the rewrite hands the backend whatever followed it. The intent is
`/admin-api/iverson.<Service>/<Method>` for gRPC-Web. Nothing in the rule limits it to that shape.

Because port 8081 serves the whole application (Pass 1), the same rule also publishes:

| External request | Rewritten to | Result |
|---|---|---|
| `GET /admin-api/metrics` | `/metrics` | 121,797 bytes of internal metrics, anonymous |
| `GET /admin-api/health` | `/health` | 4 backend operations per request, anonymous |
| `GET /admin-api/probe/sql` | `/probe/sql` | Postgres query, anonymous |
| `GET /admin-api/probe/vector` | `/probe/vector` | Qdrant collection write, anonymous |
| `POST /admin-api/probe/kafka` | `/probe/kafka` | **Kafka topic creation + produce, anonymous** |

Preconditions: none. No credential, no session, no user interaction. Note this exposure lands on
**every profile**, including the nginx ones — unlike Finding #2, it does not depend on the backend
speaking HTTP/2, because 8081 is a plain HTTP/1.1 listener that every ingress controller proxies
happily by default.

`/admin/*` stays protected: `RequireAuthorization("Operator")` is applied at the endpoint, so
`/admin-api/admin/dlq` still 403s. The exposure is precisely the seven anonymous routes.

**Evidence / Trace:**
```csharp
// Program.cs:275 — anonymous, and not bound to any particular listener  ← VULNERABLE
app.MapPrometheusScrapingEndpoint().AllowAnonymous();
```
```csharp
// Program.cs:354-359 — anonymous POST with an unbounded Kafka write  ← VULNERABLE
app.MapPost("/probe/kafka", async (IEventProducer producer) =>
{
    await producer.ProduceAsync("iverson.probe", "probe", new { timestamp = DateTime.UtcNow, traceId });
    return Results.Ok(new { produced = true, topic = "iverson.probe", traceId });
}).WithName("ProbeKafka").AllowAnonymous();
```
Spec rule (paraphrased from the Transport section): `path: /admin-api(/|$)(.*)`,
`rewrite-target: /$2`, backend port `8081`. ← **the `(.*)` is the catch-all**

**Remediation:**
- Primary fix: narrow the capture to the gRPC-Web path shape instead of `(.*)`. gRPC paths are
  `/<package>.<Service>/<Method>`, so anchor on the package prefix the console actually calls:
  ```yaml
  - path: /admin-api/(iverson\.[A-Za-z0-9_.]+/[A-Za-z0-9_]+)$
    pathType: ImplementationSpecific
    backend: { service: { name: <release>-api, port: { number: 8081 } } }
  # rewrite-target: /$1
  ```
  This routes exactly the console's RPCs and leaves `/metrics`, `/health`, and `/probe/*`
  unroutable from outside, with no reliance on the endpoints' own auth posture.
- Architectural improvement: make the listener split a real boundary rather than a convention —
  bind the operational endpoints to one listener with `RequireHost("*:8081")` and the gRPC surface
  to the other, so a routing mistake cannot cross them. Fixing Finding #4 (authenticating the
  probes) removes the impact independently of routing.
- Defense-in-depth: an ingress-level deny rule for `/admin-api/metrics` and `/admin-api/probe/*`,
  so a future widening of the path regex cannot silently re-expose them.

### Finding #2: `/metrics` and all probes answer anonymously on the gRPC listener, which the existing Ingress already routes

**Vulnerability:** Security Misconfiguration / Information Disclosure — A05
**Severity:** Medium
**Confidence:** Confirmed in-cluster; **Requires Verification** for external reachability on AWS
**Attack Complexity:** Low

**Location:**
- File: `Iverson.Server/Iverson.Api/Program.cs`, Lines: 275, 301-359 (no `RequireHost` anywhere in the file)
- Related: `charts/api/templates/ingress.yaml:18-24`; `values-aws.yaml:75`; `appsettings.json:9-17`

**Risk & Exploit Path:**
This finding refutes the standing assumption — carried in the design docs and in CDR round 6 — that
the anonymous endpoints are reachable only on 8081 and therefore safe because 8081 has no ingress
route. They are equally served on 8080, and the api Ingress routes `/` (a `Prefix` match, i.e.
everything) to 8080 today. The `/admin-api` rule is not what introduces this surface to the edge; it
only makes it trivially reachable over HTTP/1.1.

Whether an outside caller reaches it **today** depends on the profile, and the two diverge:

- **nginx profiles (`values-local.yaml:74-78`, base `values.yaml`)** — no
  `nginx.ingress.kubernetes.io/backend-protocol` annotation exists anywhere in the chart, so
  ingress-nginx proxies HTTP/1.1 to a listener that speaks only h2c. Those requests get 400.
  **Not currently reachable.**
- **AWS (`values-aws.yaml:75`)** — `backend-protocol-version: GRPC` makes the ALB speak HTTP/2 to
  the target. An HTTP/2 request for `/metrics` or `POST /probe/kafka` would be forwarded to 8080,
  where it is served. **I could not test this** — no AWS environment is available here, and ALB's
  exact handling of a non-gRPC HTTP/2 request against a gRPC-protocol target group (it may answer
  464 for protocol mismatch) decides the outcome. **Requires Verification** before this is treated
  as either exploitable or safe.

The anonymous metrics body discloses internal topology: `server_address` labels naming
`authentik-server`, `jaeger`, `ollama`, `qdrant`, plus a pod IP `10.89.0.27` and a
`service_instance_id`. That is a cluster map for anyone planning lateral movement.

**Evidence / Trace:**
```
# Confirmed live on the gRPC listener — the port the Ingress routes to  ← VULNERABLE
$ curl --http2-prior-knowledge http://localhost:8080/metrics   → HTTP 200, 121797 bytes
$ curl --http2-prior-knowledge http://localhost:8080/probe/sql → HTTP 200 {"connected":true,...}
```
```json
// appsettings.json:9-17 — the split that is a protocol convention, not a boundary
"Grpc": { "Url": "http://*:8080", "Protocols": "Http2" },
"Http": { "Url": "http://*:8081", "Protocols": "Http1" }
```
```yaml
# charts/api/templates/ingress.yaml:18-24 — Prefix "/" catches every path  ← VULNERABLE
- path: /
  pathType: Prefix
  backend: { service: { port: { number: 8080 } } }
```

**Remediation:**
- Primary fix: authenticate the operational endpoints (Finding #4) — that closes this regardless of
  which listener or ingress reaches them, and is the only fix that does not depend on
  protocol-level accidents.
- Architectural improvement: bind them explicitly with `RequireHost` so "operational endpoints live
  on 8081" becomes enforced rather than assumed.
- Defense-in-depth: **verify the AWS behaviour directly** — send `GET /metrics` and
  `POST /probe/kafka` over HTTP/2 to a deployed ALB and record the response. That single test
  converts this finding from Requires Verification to either closed or High.

### Finding #3: NetworkPolicy opens port 8081 to every source in the cluster while documenting it as kubelet-only

**Vulnerability:** Broken Access Control / permissive network rule in IaC — A01, A05
**Severity:** Medium
**Confidence:** Confirmed
**Attack Complexity:** Low (given any foothold in the cluster)

**Location:**
- File: `Iverson.Server/deploy/helm/iverson/templates/networkpolicies.yaml`, Lines: 28-33

**Risk & Exploit Path:**
The rule's `from: []` is an **empty source selector, which in Kubernetes NetworkPolicy semantics
matches all sources** — the field being empty means "this rule matches all sources", not "no
sources". The comment describes the intent as kubelet readiness/liveness probes and calls the port
"the dedicated Http1 health port", but port 8081 is not a health port: it serves the entire
application, including all seven anonymous endpoints and every authenticated one.

Result: any pod anywhere in the cluster — a compromised sidecar, a co-tenant workload, a
build-agent pod — can reach the api's full REST surface directly by pod IP, bypassing the ingress
entirely. The namespace default-deny at `:7-10` is correctly in place and this rule punches
through it. App-level authn still protects `/admin/*` and `/v1/traces`; the anonymous seven have
nothing in front of them.

Contrast the sibling rule immediately above, which is correctly scoped:
```yaml
# networkpolicies.yaml:22-27 — correctly restricted to one namespace
- from:
    - namespaceSelector:
        matchLabels: { kubernetes.io/metadata.name: ingress-nginx }
  ports: [{ protocol: TCP, port: 8080 }]
```
```yaml
# networkpolicies.yaml:28-33 — empty `from` matches every source  ← VULNERABLE
- from: []   # kubelet readiness/liveness probes: ...
  ports: [{ protocol: TCP, port: 8081 }]
```

**Remediation:**
- Primary fix: the kubelet connects from the node IP, so scope the rule to the node network instead
  of to everything:
  ```yaml
  - from:
      - ipBlock: { cidr: <node-subnet-cidr> }
    ports: [{ protocol: TCP, port: 8081 }]
  ```
  If the node CIDR is not knowable at template time, expose a dedicated probe port serving only
  `/health/live` and leave the application's port closed to arbitrary sources.
- Architectural improvement: split the health endpoints onto their own Kestrel listener so a
  network rule that must stay broad grants access to nothing but liveness.
- Defense-in-depth: correct the comment. It currently asserts a scope the rule does not implement,
  which is how this survives review.

### Finding #4: Anonymous endpoints perform unbounded backend writes — unauthenticated resource consumption

**Vulnerability:** Unrestricted Resource Consumption / Missing Function-Level Authorization — A05, A01
**Severity:** Medium
**Confidence:** Confirmed
**Attack Complexity:** Low

**Location:**
- File: `Iverson.Server/Iverson.Api/Program.cs`, Lines: 301-334 (`/health`), 348-352 (`/probe/vector`), 354-359 (`/probe/kafka`)

**Risk & Exploit Path:**
These are not read-only health reporters. Each anonymous call does real work against four
datastores, with no authentication, no rate limiting, and no idempotency guard:

- `GET /health` fans out to **all four** backends per request — Postgres query, StarRocks health
  check, Qdrant `EnsureCollectionAsync("iverson-probe", 4)`, and a Kafka `ProduceAsync` to
  `iverson.health.probe`. One cheap HTTP request costs four backend operations: a ~4× amplification
  primitive against the stack's own datastores.
- `POST /probe/kafka` produces a message to `iverson.probe` on every call, unbounded.

**Confirmed empirically, and stronger than expected:** the `iverson.probe` topic did not exist
before testing (`GetOffsetShell` → "Could not match any topic-partitions"). After a single
anonymous POST it exists with 12 partitions. `iverson.health.probe` likewise exists, created by
the anonymous `/health` path. **An unauthenticated request creates Kafka topics** through broker
auto-create — not merely writing to a pre-provisioned topic, but provisioning cluster resources.

Reachability today is bounded by Findings #2 and #3 (in-cluster confirmed; external unverified),
which is why this is Medium and not High. Finding #1 would remove that bound entirely.

**Evidence / Trace:**
```csharp
// Program.cs:308-313 — four backend calls per anonymous request  ← VULNERABLE
var pgTask     = db.QuerySingleOrDefaultAsync<int>("SELECT 1")...
var srTask     = sr.CheckHealthAsync();
var vectorTask = vector.EnsureCollectionAsync("iverson-probe", 4)...   // write
var kafkaTask  = kafka.ProduceAsync("iverson.health.probe", "probe", ...)  // write
```
```
# Confirmed: topic created by one anonymous, unauthenticated POST  ← VULNERABLE
BEFORE: "Could not match any topic-partitions with the specified filters"
POST /probe/kafka (anonymous) → 200 {"produced":true,"topic":"iverson.probe"}
AFTER:  iverson.probe:7:0  iverson.probe:8:0 ... (12 partitions)
```

**Remediation:**
- Primary fix: require authorization on the probes; they are operator diagnostics, not liveness
  checks, and nothing in the deployment calls them anonymously:
  ```csharp
  app.MapGet("/probe/sql", ...).WithName("ProbeSql").RequireAuthorization("Operator");
  app.MapPost("/probe/kafka", ...).WithName("ProbeKafka").RequireAuthorization("Operator");
  ```
  Keep `/health/live` anonymous (it touches nothing). For `/health`, which the kubelet does call,
  cache the fan-out result for a few seconds so request rate decouples from backend load.
- Architectural improvement: disable Kafka topic auto-create in the broker so an application bug or
  an anonymous caller cannot provision cluster resources.
- Defense-in-depth: rate-limit the anonymous endpoints with ASP.NET Core's built-in limiter.

Round 1 Finding #1 reported that `RegisterSchema` had no authorization, letting any of four JWT

and the probes in the same commit. Fix Finding #4 before fixing the annotation.

## Pass 3 — Cross-cutting & compositional analysis

**The load-bearing wrong assumption.** One belief runs through the design docs and CDR round 6:
*the anonymous endpoints live on 8081, and 8081 has no ingress route, so they are not exposed.* The
first clause is false — verified by request, not by inference. Everything downstream that rests on
it needs rechecking, and the specific reason it went unnoticed is instructive: the belief is
*operationally* true (a plain `curl` to 8080 really does return 400, which the team has observed
and recorded) while being *architecturally* false. The 400 comes from protocol negotiation, not
authorization. A protocol mismatch that happens to reject the tool you tested with is not a
boundary; it is a boundary-shaped coincidence, and it disappears the moment the client speaks h2c —
which every gRPC client in this system already does.

**Chained attack — foothold to cluster map to resource abuse.** Finding #3 gives any pod in the
cluster reach to port 8081 → Finding #2/#4 mean that port answers anonymously with a 121KB
topology dump naming `authentik-server`, `qdrant`, `ollama`, `jaeger` and a pod IP → the same
foothold can then drive `POST /probe/kafka` to create topics and `GET /health` to fan out 4×
amplified load across all four datastores. No credential is needed at any step. The api's egress
policy (`networkpolicies.yaml:43-61`) is tightly scoped and does good work here, but it constrains
what the *api* can reach, not what an attacker can make the api *do*.

**Defense-in-depth gap.** The anonymous seven have exactly zero controls in front of them: no
authn, no authz, no rate limit, no network scoping on 8081 (#3), and — if #1 ships — no routing
restriction either. Every other endpoint class in this application has at least one control.

**Implicit trust assumption.** The listener split is treated throughout the codebase and docs as a
trust boundary ("REST is on 8081", "8080 is gRPC"). It is a protocol convention. `grep -n
"RequireHost"` returning nothing is the whole proof. Until endpoints are actually bound to
listeners, any reasoning of the form "X is only on port Y" is unsound.

**Deployment context.** The chart's security posture is otherwise good — default-deny NetworkPolicy,
per-component egress allowlists, no `latest` tags, secrets via `secretKeyRef`. Finding #3 is a
single over-broad rule inside an otherwise careful policy set, which is exactly the kind of thing
that survives review because the surrounding file looks disciplined.

## 1. Executive Summary

This round was scoped to one question — does the designed `/admin-api` catch-all expose the api's
anonymous endpoints — and the answer is yes, but the more important finding is that the assumption
protecting them today is already false. The seven `AllowAnonymous` endpoints are **not** confined
to port 8081. They are served on the gRPC listener (8080) as well, confirmed by issuing h2c
requests against the running stack: `/metrics` returns 121,797 bytes, all four probes return 200,
and an anonymous `POST /probe/kafka` **created a Kafka topic** that did not previously exist. Port
8080 is the port the existing api Ingress already routes `/` to.

The endpoints are also not the passive health reporters their names suggest. `GET /health` fans out
to Postgres, StarRocks, Qdrant, and Kafka on every call — two of those are writes — making one
unauthenticated HTTP request cost four backend operations. Combined with a NetworkPolicy rule whose
`from: []` opens port 8081 to every source in the cluster while its comment describes it as
kubelet-only, any foothold in the cluster gets an anonymous cluster topology dump and an
amplification primitive. If the `/admin-api` rule ships with its `(.*)` catch-all, all of it becomes
reachable from the internet on every profile, including the nginx ones.

**Production readiness:** the current tree is deployable with a remediation commitment — external
reachability today is bounded by protocol accidents rather than controls, which is not a posture to
rely on but is not presently breached either. **The `/admin-api` Ingress must not ship as specified.**
Narrowing its path regex is a small change and is best made now, before implementation, alongside
authenticating the probes — that pair closes the exposure from both directions. One item is
explicitly unresolved and needs a live test rather than more reading: whether AWS's ALB, configured
with `backend-protocol-version: GRPC`, forwards a non-gRPC HTTP/2 request to `/metrics`. If it does,
Finding #2 is already live in production and becomes High.

## 4. Positive Security Observations

1. **Round 1's Critical was genuinely fixed, not papered over.** `RegisterSchema` moved behind
   `[Authorize(Policy = "SchemaAdmin")]` (`ObjectMappingGrpcService.cs:38`) *and* the inline
   registry mutation was replaced by a dedicated registration service. The fix addressed the
   mechanism, not just the symptom.
2. **Authorization denials are audited by construction.**
   `AuditingAuthorizationMiddlewareResultHandler.cs:8` registers `SchemaAdmin`, `Operator`, and
   `TenantAdmin` as audited policies through a global `IAuthorizationMiddlewareResultHandler`, so
   audit coverage does not depend on each endpoint remembering to log.
3. **Secure-by-default authorization posture.** A `FallbackPolicy` of `RequireAuthenticatedUser()`
   (`Program.cs:143-145`) means endpoints are authenticated unless explicitly opted out — the safe
   default direction. Every anonymous endpoint in this report is a deliberate, greppable
   `AllowAnonymous`, which is why a complete inventory took one command.
4. **NetworkPolicy egress is tightly and thoughtfully scoped.** `networkpolicies.yaml:43-61` allowlists
   each datastore by port and pod selector, with a comment explaining why StarRocks is matched on
   `ownerreference/name` rather than the cluster label. Finding #3 is one over-broad ingress rule in
   an otherwise disciplined policy set.
5. **`MapInboundClaims = false` with a recorded reason** (`Program.cs:106-112`) — the legacy
   WS-Federation claim remapping would have silently broken `sub` lookups. The comment documents the
   failure mode and how it was confirmed.

## 5. Prioritized Remediation Roadmap

1. **Finding #1 — narrow the `/admin-api` path regex before implementing it.**
   Highest priority by a wide margin: it is the only High, it is the difference between the current
   74 and a projected 54, and it costs nothing right now because the Ingress has not been written.
   Anchoring the capture on the `iverson.<Service>/<Method>` shape routes exactly the console's RPCs
   and leaves the anonymous surface unroutable.
   *Effort:* Quick Win (pre-implementation). *Owner:* DevOps + Backend.

2. **Finding #4 — require `Operator` on the four probes; cache `/health`'s fan-out.**
   Prioritized second because it is the only fix that closes the exposure *independently of routing
   and protocol* — it holds no matter what any ingress does later. It also removes the topic-creation
   primitive. Keep `/health/live` anonymous.
   *Effort:* Quick Win. *Owner:* Backend.

3. **Finding #2 — verify the AWS ALB behaviour, then bind endpoints to listeners.**
   The verification is one request against a deployed ALB and it decides whether this is already
   live in production; that answer should not stay unknown. The `RequireHost` binding then converts
   the listener split from convention into an enforced boundary.
   *Effort:* Quick Win (test) / Moderate (binding). *Owner:* DevOps + Backend.

4. **Finding #3 — scope the port-8081 NetworkPolicy rule to the node CIDR.**
   Prioritized fourth because it needs a cluster foothold to matter, but it is a small edit that
   removes a cluster-wide hole, and correcting the misleading comment prevents the next reviewer
   from re-approving it.
   *Effort:* Quick Win. *Owner:* DevOps.

5. **I-2 — do not add the nginx `backend-protocol: "GRPC"` annotation until #4 lands.**
   Not a vulnerability, but a sequencing hazard worth holding in the roadmap: the commit that makes
   gRPC work through the nginx ingress is the same commit that would publish `/metrics` and the
   probes on those profiles. Order matters.
   *Effort:* Quick Win (sequencing discipline). *Owner:* DevOps.

**Out of scope this round:** dependency/CVE scanning of the .NET and container surface, and the
gRPC services' own authorization logic beyond the prior-art recheck. The focus hint scoped this to
the `/admin-api` exposure question. A future round without a focus hint should cover both.
