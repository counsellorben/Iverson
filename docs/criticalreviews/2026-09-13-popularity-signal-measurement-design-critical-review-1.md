### 2.1 Step 4's `--pair` scorer refuses the arms by design: `check_pool` requires an identical per-query document **set**, and a fused popularity weight changes which 50 documents are recorded

**Description.** Step 4 prescribes `report.py --pair RUN=BASELINE`, described as a check that "checks pool invariance before comparing". `check_pool` is not a diagnostic — it is a hard precondition that `sys.exit`s. It requires, for every query, `set(run_seq[q]) == set(base_seq[q])`, on the stated premise that "Reranking rescores the documents the control already selected". That premise is true for the cross-encoder experiment it was written for and false here: `WPopularity` is fused *inside* the server (`ResultReranker.Rerank`) over the 4× over-fetched 200-candidate pool, and only then trimmed to the recorded 50. Any document that crosses the rank-50 boundary under the popularity term changes the set, and the whole point of the treatment arm is to move documents. The run aborts with "ARM INVALID: pool changed … this arm was produced by a different pool and must not be scored" before any statistic is computed — so Phase 2 produces no numbers at all, for either RPC.

**Evidence (file:line).** `Iverson.Server/Iverson.LoadTest/scripts/report.py:732-759` (`check_pool`: `set_changed = [q for q in common if set(run_seq[q]) != set(base_seq[q])]` → `sys.exit`), `:784` (`for run_path, baseline_path in pairs: check_pool(run_path, baseline_path)` — unconditional, before `baseline_runs` is built). A document that moves 29 ranks inside the recorded 50 will also cross the 50/51 boundary from outside it — ranks 51-200 are unrecorded but sit immediately below rank 50 (median adjacent-rank gap inside the pool is 0.00124, while the popularity term's reachable swing is `W·(p_max − p_min)` ≈ 0.090 in fused units, 72× that gap).

**Proposed fix.** Replace Step 4's single `--pair` invocation with a scoring route that does not assert set invariance, and say which: either (a) run `report.py --baseline <control run> …` once per RPC — `check_pool` is called only from `run_pair_statistics` (`:784`), never from `run_paired_statistics` (`:630-698`) — and apply Holm across the two RPC results by hand, since `--baseline` accepts a single baseline file and so cannot hold both RPCs in one family; or (b) extend `check_pool` with an explicit fusion-arm mode that keeps the second half (the ≥25% reordered-sequence floor, `POOL_MIN_REORDERED_FRACTION` at `:700`, which still catches "the arm never applied") and drops the set-equality half, and record that change as part of this work. Whichever is chosen, Step 4's sentence "which checks pool invariance before comparing" must stop describing the check as a feature this experiment passes.

`Evidence:` [presence] `grep -n 'check_pool' report.py` → definition at `:732`, single call site at `:784` inside `run_pair_statistics`; `run_paired_statistics` (`:630`) contains no call, so route (a) exists. [presence] `--baseline` is one path (`baseline_abspath = os.path.abspath(baseline_path)`, `:643`) and Holm runs over `compare_paths` within one measure (`:673-680`), so a single invocation cannot form the two-RPC family — the manual-Holm caveat in (a) is not optional. [totality] the set-change claim is run-tier: simulated over all 300 recorded pools as described above (median max movement 29 ranks), not inferred from the formula alone.

### 2.4 Phase 1's identity has no branch for candidates with no citation count — ~8% of the corpus, and the shipped reranker treats them as `fused_new = fused_old`

**Description.** "The identity that makes it exact" states one formula, `fused_new = (0.90·fused_old + W·pop)/(0.90 + W)`, and the prerequisite section closes exactly one gap in it: candidates without a centroid, whose divisor is 0.45. It closes nothing for candidates without a `pop` operand at all. The spec's own Phase 2 text says roughly 6% of documents will not resolve and that the primary arm leaves their payload absent — and `ResultReranker` adds `WPopularity` to the numerator **and** the weight total only when `candidate.Popularity is not null`, so an absent count leaves that candidate at `(0.45·base + 0.45·centroid)/0.90`, i.e. exactly `fused_old`, while every other candidate in the pool moves. Applying the stated identity to every candidate (with, say, `pop = 0` or the median) models a transform the server does not implement, on ~3-4 documents per 50-document pool — the same divisor-mismatch defect class the centroid prerequisite exists to rule out, in a larger population.

**Evidence (file:line).** `Iverson.Server/Iverson.Vector/ResultReranker.cs:53-57` (`if (hasPopularity) { weightedSum += _o.WPopularity * …; weightTotal += _o.WPopularity; }`), `:22-23` (`hasPopularity = candidate.Popularity is not null`), `ObjectSearchGrpcService.cs:1048-1049` (`PopularityFor` returns null when the payload key is absent or unparseable). **Proposed fix.** State the absent-count branch alongside the divisor branch in "The identity that makes it exact": a candidate with no resolved citation count keeps `fused_new = fused_old` (weight total stays 0.90, no numerator term), matching `ResultReranker`'s `hasPopularity` gate — and note that this is *not* the same as `pop = 0`, which the Pre-registration section already distinguishes. `Evidence:` [presence] the two ResultReranker line ranges above were read in full; the `hasPopularity`-false path is the pre-existing `(WBase·base + WCentroid·centroid)/(WBase+WCentroid)` expression with `WBase = WCentroid = 0.45` (`VectorRankingOptions.cs`), which is `fused_old` by definition. ### 2.5 "A conservative bias, stated" has the direction backwards: offline re-ranking of the recorded 50 **overstates** the treatment, because the promotions it cannot see are almost all non-relevant

**Description.** The section argues that because the server ranks 200 candidates while the run file records 50, "Offline re-ranking cannot see a document promoted from rank 51 … This **understates** the ceiling, so a screen that clears the bar on the truncated pool would also clear it on the full one." The missing promotions are not a one-sided loss of upside. Promotions from that region are therefore ≈99.9% non-relevant, and their systematic effect is to *dilute* the live top-10 relative to the offline estimate. The offline screen is optimistic, not conservative, and "clears offline ⇒ clears live" does not follow. The error matters because the same sentence is the stated reason the bias "is not corrected".

**Evidence (file:line).** Spec lines 243-248 ("A conservative bias, stated"). **Proposed fix.** Restate the bias with its real sign: offline re-ranking omits promotions from ranks 51-200, which are overwhelmingly non-relevant, so the offline ceiling is an **upper** estimate of the live one and a Phase 1 PASS does not guarantee a Phase 2 PASS. `Evidence:` [totality] the 311/339 in-pool count is computed over the complete judgment set and the complete run file, not sampled; the ≤28 residual is arithmetic on those totals. [totality] the 29-rank median movement and the 88% swing-vs-gap fraction are computed over all 300 pools using the spec's own identity and `W` rule. [presence] `BenchmarkQueryScenario.cs:42` `DocumentBudget = 50` and `ObjectSearchGrpcService.cs:943` `OverFetchFactor = 4` are the 50-vs-200 asymmetry the finding rests on. ## 3. Forced decisions

### 3.1 How the age covariate is operationalised — stratum granularity and the count-but-no-date population — and the Phase 1 gate binds on the answer

**The choice.** Measurement 4c permutes citation counts "*within* age strata" and the Gate makes that null "the binding comparison". The spec fixes the threshold (0.0152) but not the null: neither the stratum definition (calendar width? quantiles? `year` vs month-granular `publicationDate`?) nor what happens to documents that have a resolved count and no date. Measurement 4d's `count / age` has the same no-date population and an unstated denominator convention.

**Why it's forced.** The stratification is not a presentation detail — it determines the gate's outcome across its whole range. At coarse strata the permutation approaches measurement 3's plain shuffle and the age-preserving null stops controlling for age; at fine strata most strata hold one document, the permutation approaches the identity, the null ceiling approaches the real ceiling, and the gate cannot be cleared by any signal. The spec's own data properties force the question rather than leaving it open: `publicationDate` is month-granular "occasionally day-granular", and dates are "separately nullable" from counts, so a no-date subset of unknown size is guaranteed to exist and cannot be placed in any date stratum. Choosing after seeing the real and null ceilings is exactly the researcher degree of freedom the rest of the pre-registration is built to remove — and unlike `S` and `W`, no rule is stated to execute.

**Options.**

- **(a) Fixed calendar strata (e.g. 5-year bins on `publicationDate`, falling back to `year`), with no-date rows forming their own stratum permuted among themselves.** Keeps every document in both the real and the null ceiling, so the two ceilings are computed over identical populations. The no-date stratum preserves no age structure by construction, so it behaves like a plain shuffle for that subset — which is honest only if its size is reported. `Evidence:` [presence] `fetch_citations.py:66-71` writes `years` and `dates` as separately-guarded assignments, so the no-date subset is a real, enumerable population in the fetch output; its size is not yet measurable — UNVERIFIED: no dates have been fetched (`citations-countonly.json.bak` has no `years`/`dates` keys, and `corpus.jsonl` carries `metadata: {}`), so the fraction and the resulting stratum sizes cannot be estimated in-round.
- **(b) Quantile strata (e.g. date deciles over the resolved-date population), excluding no-date rows from both the real and the null ceiling.** Equalises stratum occupancy, so the degeneracy risk is bounded by a chosen decile count rather than by the corpus's date distribution; costs a like-for-like reduction of the pool (both ceilings recomputed on a smaller candidate set, which is not the pool Phase 2 will rank). `Evidence:` [presence] pools are 50 documents each and 300 queries wide (measured on the run file), so a decile scheme over the corpus leaves ~5 documents per stratum per pool — non-degenerate but coarse; UNVERIFIED: whether deciles over the real date distribution are non-degenerate depends on date ties (month granularity), unmeasurable before the fetch.
- **(c) Drop the stratified permutation and residualise instead: regress count on age over the corpus, permute the residuals, and rebuild counts.** Removes the granularity choice entirely (no bins), at the cost of imposing a functional form on the age-count relationship that the spec has not measured and that measurement 4a is supposed to characterise first. `Evidence:` [absence] UNVERIFIED — 4a (AUC of publication date alone) has not been run; no evidence exists in-round about the shape of the age-count relation on this corpus, which is precisely what makes this option a modelling assumption rather than a mechanical rule.

**Why no combination dominates.** (a) and (b) differ irreducibly in *which* population the gate is computed over — all documents with a degenerate no-date stratum, versus resolved-date documents only — and that difference moves the comparison in opposite directions depending on how large and how citation-heavy the no-date subset turns out to be; neither can be shown better before the fetch reports that subset. (c) removes the binning question but substitutes an unmeasured functional form, so it is not a strict improvement on either. A hybrid — (b)'s quantile bins with (a)'s no-date stratum retained — is available and is the closest thing to a dominant variant, but it inherits (a)'s honesty caveat (a stratum with no age structure inside an age-preserving null) rather than resolving it, so it is a fourth choice on the same axis, not a free win. What the spec needs is one of these written down *before* the ceilings are computed, together with the resolved/no-date split it already promises to report.
