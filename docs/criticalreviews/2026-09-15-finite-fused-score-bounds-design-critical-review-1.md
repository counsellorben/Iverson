## 2. Literal-wrongness findings

### 2.1 A negative `<relation>Count` is a producible input that the design neither closes nor scopes out, so the spec's totality claims are false

**Description.** The spec says its bounds make popularity finite "for any payload the parsers accept" (Why 10⁶) and "for every parseable input" (row 4). It says the counts are non-negative because the consumer is "the only writer" (row 6), and that every admitted configuration "over each signal's full range fuses to a finite score". The popularity readers parse the count with `long.TryParse(stored, out var count)` (`ObjectSearchGrpcService.cs:1006`, `:1048`), which accepts a sign. A second writer can put a negative value under the same key: the object upsert's `BuildObjectPointPayload` writes every scalar and vector-field property under its camelCase name (`IntelligenceStoreConsumer.cs:437`, `:450`). A parent type with a denormalized `CommentsCount` property and a `Comments` popularity signal is one example, and nothing rejects that collision. When `count + RecencyBoost × D = −SaturationPoint`, `effective / (effective + S)` divides by zero. Popularity becomes −∞, and the fused score is NaN even at `WPopularity = 0` (the same `0 × ∞` mechanism as Problem 1), under every configuration the new rules admit. Some of these payloads turn non-finite only because of an admitted `RecencyBoost`: a count of −150 with a future-dated bucket of 100 is finite at boost 0 (−150/−100 = 1.5) and NaN at boost 1 with S = 50. So the stated outcome, that no admitted `RecencyBoost` value can make a fused score non-finite, does not hold over the inputs the system can produce.
